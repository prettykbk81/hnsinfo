# 변화 감지 + 원인 추적

## 핵심 원칙

**"뭐가 변했는지"를 찾고, "왜 변했는지"를 밝히는 것이 이 스킬의 전부다.**

안정적인 것은 다루지 않는다. 변화가 있는 곳만 파고든다. 변화의 원인을 모르면 웹서치한다. 웹서치로도 못 찾으면 "미확인"이라고 솔직히 말한다.

---

## 데이터 수집

**업종 전체 변화 감지:**
```
industry_analysis(industry: "[업종코드]", dateType: "m", date: "최근 월말", mode: "full")
```
→ `changes_detected` 필드에 유의미한 변화가 자동 감지되어 반환됨

**특정 앱 변화 추적:**
```
app_health_check(pkgName: "패키지명", dateType: "m", startDate: "6개월 전", endDate: "현재")
```

## 분석 프로세스

### 1. 변화 감지

`changes_detected`에서:
- MAU 10%+ 변동 = 유의미
- 사용시간 15%+ 변동 = 유의미
- 변화량 큰 순으로 정렬하여 상위 3~5개에 집중

변화가 없으면:
- "이번 기간 유의미한 변화 없음"으로 시작
- 대신 "변화가 없다는 것 자체의 의미"를 해석 (시장 포화? 안정기? 경쟁 교착?)

### 2. 변화 유형 분류

| 유형 | 패턴 | 의미 |
|------|------|------|
| 스파이크 | 특정 월만 급등 후 하락 | 이벤트/콘텐츠 효과 (일시적) |
| 구조적 상승 | 3개월+ 연속 상승 | 진짜 성장 |
| 구조적 하락 | 3개월+ 연속 하락 | 이탈 가속 |
| 급락 | 전월 대비 -15%+ | 사건 발생 (이슈, 규제, 경쟁) |
| 반등 | 하락 후 상승 전환 | Live Ops 효과 또는 시즌 |

### 3. 원인 추적 (웹서치 필수)

변화 유형에 따라 검색. **앱당 최소 2회 이상 검색**하여 원인을 특정한다.

**검색 전략:**
- 스파이크 → "{앱명} 신작/이벤트/프로모션 {해당 월}" + "{앱명} 이용자 급증 {해당 월}"
- 구조적 상승 → "{앱명} 성장 이유 {해당 연도}" + "{앱명} 신규 서비스 {해당 연도}"
- 급락 → "{앱명} 이슈/사건/규제 {해당 월}" + "{앱명} 해지/이탈 {해당 월}"
- 반등 → "{앱명} 업데이트/복귀 이벤트 {해당 월}" + "{앱명} 신작 {해당 월}"

**원인 기술 3요소 (반드시 채울 것):**
1. **무엇이** — 구체적 콘텐츠명/이벤트명/정책명
2. **언제** — 정확한 날짜 또는 주차
3. **얼마나** — 효과 크기 (수치 또는 정성적 판단)

**하락 원인은 2가지를 구분:**
- 자체 요인: 콘텐츠 공백, 요금 인상, 서비스 장애
- 경쟁 요인: 경쟁사 히트작, 경쟁사 프로모션, 시장 구조 변화
- "콘텐츠 공백"이라고만 쓰지 말고, 실제로 그 달에 뭘 냈는지 확인 후 판단

**못 찾으면:** "원인 미확인"으로 명시. 추측 금지.

### 4. 지속성 판단

변화가 감지되면 "이게 계속될 것인가?" 판단:
- 스파이크 후 4주 유지율 확인 → 10%+ 유지면 "습관 형성", 미만이면 "일시적"
- 구조적 변화면 → "이 추세가 반전될 조건은 무엇인가?" 제시
- 급락이면 → "바닥은 어디인가? 반등 조건은?" 제시

### 5. 인사이트 출력

1. "가장 큰 변화: [앱명]이 [X]% [상승/하락]. 원인: [Y]." — 한 문장
2. 지속성 판단: "이 변화는 [일시적/구조적]이다. 근거: [Z]."
3. 의미: "이것이 시장/경쟁에 미치는 영향은 [W]이다."
4. 액션: "지금 해야 할 것 2개"

---

## 출력 규칙

- 변화가 없으면 "없다"고 말한다 (억지로 인사이트를 만들지 않는다)
- 원인을 못 찾으면 "미확인"이라고 한다 (지어내지 않는다)
- 모든 변화에 "일시적 vs 구조적" 구분을 붙인다
- 웹서치 결과는 출처 명시
- "판정", "판단", "확인" 같은 딱딱한 워딩 쓰지 않는다
- "~인 것으로 보입니다" 금지
- `suggested_searches`가 있으면 반드시 웹서치 실행

## 업종 맥락 참조
